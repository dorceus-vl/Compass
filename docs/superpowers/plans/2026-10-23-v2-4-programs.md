# Compass v2.4 (Programs, portfolio budget, workload) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Group projects into **programs** with a roll-up, Vlad's own RAG and a program report; give the Portfolio a **budget line** (forecast, currency, roll-ups); add **Workload**: estimate hours per week against the capacity he sets.

**Architecture:**
- **Schema:** one migration, `0017_programs.sql`: table `programs`, and `projects.program_id`, `budget_forecast`, `currency`.
- **Computed on the device:** the program roll-up, budget totals and Workload are pure functions in `shared/` over the offline mirror (projects, tasks, milestones) plus one program detail answer (baselines, top risks, pending changes). No server aggregation, so they work offline, as the v2.2 Dashboard.
- **Server-side:** programs CRUD, the detail route (subselects only), the program summary for the report (same shared roll-up, numbers only through `runAi`).

**Tech Stack:** As before: Hono on Workers + D1, React + Vite, plain CSS with tokens, hand-drawn SVG charts (`web/src/ui/Chart.tsx`). No new dependency.

**Spec:** `docs/superpowers/specs/2026-10-23-v2-4-programs-design.md` (approved by Vlad on 2026-10-23). Read it with this plan.

## Rulings made while writing this plan

- **P1: kind is fixed.** A project's `kind` can't change after creation (verified), so the spec's "a kind change clears the program" needs no code: the same-kind check runs when `program_id` is set (PATCH or POST of a project). A program's `kind` is also fixed after creation (PATCH refuses `kind`, 400 `program_kind_fixed`).
- **P2: navigation.** `Workload` joins `NAV` after Calendar (icon `calendar` reused unless DESIGN.md has a better one). Programs live on the Projects screen: a segmented control **Projects | Programs** at the top (`/projects` and `/programs`), and `/programs/:id` for one program. Both added to the Palette jumps.
- **P3: the detail answer.**
  ```ts
  interface ProgramDetail {
    program: Program;
    baselines: { project_id: string; snapshot: Snapshot; taken_at: string }[]; // latest live per member, opened
    risks: { id: string; project_id: string; title: string; probability: number; impact: number }[]; // top 10 open by p×i, opened
    pending_changes: { project_id: string; n: number }[];
  }
  ```
  Latest baseline per member: `SELECT b.* FROM baselines b WHERE b.deleted_at IS NULL AND b.project_id IN (members) AND b.taken_at = (SELECT MAX(o.taken_at) FROM baselines o WHERE o.project_id = b.project_id AND o.deleted_at IS NULL) LIMIT 500`.
- **P4: estimates.** `parseEstimate(s, dayHours)` accepts `90`, `30m`, `2h`, `1.5h`, `1d`, `1.5d`, `1h 30m` (case-insensitive, spaces allowed), returns integer minutes or `null` for a bad or empty string; the cap is `40 * dayHours * 60`. `formatEstimate(min)` → `1h 30m`, `45m`, `0m`. Server check: `estimate_minutes` integer 0–57,600 or null, else 400 `bad_estimate`.
- **P5: workload placement** (spec §3), all days in `settings.tz` via `localDay`:
  - range = [max(startDay, today), dueDay] when both dates exist and dueDay ≥ today; hours split evenly over its Mon–Fri days; no weekday in the range → all on dueDay;
  - due only, dueDay ≥ today → dueDay; dueDay < today (overdue, with or without start) → today, flagged `overdue`;
  - start only or neither → `unscheduled`;
  - a day on a weekend from the "due only" or "no weekday" cases stays on that day (Vlad set it so).
  - Leaf rule: a task counts only if no live, not-done task has `parent_id` = its id.
  - Capacity for week `w`: `overrides[w] ?? { work: work_hours, personal: personal_hours }`; the current week is multiplied by `weekdaysLeft / 5` where `weekdaysLeft` counts Mon–Fri days from today to Friday (Saturday/Sunday today → 0, so the current week's capacity is 0 and any hours there are "over").
- **P6: budget maths.** variance = forecast − planned (null if either is null); `% spent` = spent / planned (null if planned is null or 0). Totals grouped by `currency`; a project with no `budget_planned` contributes to no total. Amounts shown with `Intl.NumberFormat(undefined, { style: 'currency', currency })`.
- **P7: the program report summary.** `POST /api/reports/status {program_id}` (exactly one of `project_id`, `program_id`) loads in one `DB.batch`: the program, members (`SELECT * FROM projects WHERE program_id = ?1 AND deleted_at IS NULL LIMIT 500`), their top-level tasks, milestones and latest baselines (subselects, P3), open risk counts. If the program is missing or trashed → 404; any member with `data_boundary = 'offline'` → 200 with `ai_refused: 'offline_boundary'` and no summary. Else `programRollup()` → `programReportText()` (numbers and RAG words only) → `runAi`. The thread kind follows the program's kind.
- **P8: purge.** Programs past 30 days in Trash: in the purge batch, before `DELETE FROM projects`, add `UPDATE projects SET program_id = NULL WHERE program_id IN (SELECT id FROM programs WHERE deleted_at IS NOT NULL AND deleted_at < ?1)` then `DELETE FROM programs WHERE deleted_at IS NOT NULL AND deleted_at < ?1` (after the projects delete, so a purged project pointing at a purged program is gone first either way).
- **P9: settings shape.**
  ```ts
  workload: { work_hours: number; personal_hours: number; day_hours: number; default_estimate_minutes: number;
              overrides: Record<string, { work: number; personal: number }> }
  // defaults: 40, 8, 8, 60, {}
  ```
  PATCH accepts a partial `workload`; checks: hours 0–168, `day_hours` 1–24, default 0–2,400, override keys are Mondays `YYYY-MM-DD`, values 0–168, at most 104 keys (a `null` value removes a key). Errors 400 with a plain message.
